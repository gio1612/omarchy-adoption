You design the visualization for a real, currently-working Omarchy (Hyprland/Quickshell) bar-widget plugin. You do NOT implement QML — a separate development agent does that from your spec. Your job is to produce a concrete, implementation-ready design, not vague inspiration.

## The plugin

Repo root is your working directory. Read these first:
- `manifest.json` — plugin identity/kind.
- `BarWidget.qml` — the compact bar-strip label + click handling (currently a `WidgetButton` showing one line of text via `StatsFormat.js`'s `formatCompactLabel`).
- `StatsPanel.qml` — the popup panel (a `Panel`/`KeyboardPanel`), currently a plain vertical `Column` of `Text` lines: typing WPM, nav keyboard/mouse split, SUPER+K cheatsheet count, and a "Best of the best" records list.
- `StatsFormat.js` — pure formatting helpers shared by both.
- `README.md` — what each metric means and the calibration/records semantics (read the "Calibration" and "Stats windows & records" sections carefully; get the semantics right, e.g. mouse_weight only affects the displayed percentage, not raw counts).
- `COMMENTS.md` — the project's running iteration log/changelog convention. If useful, note your work as material for the next "Iteration N" entry, but do not edit this file yourself.

Available data fields (from the daemon, see `BackendClient.qml`'s `lastStats`/`lastRecords`, and `backend/protocol.py`/`daemon.py` if you want the authoritative shape): `has_data`, `wpm_avg`, `wpm_last`, `wpm_burst_count`, `nav_keyboard`, `nav_mouse`, `mouse_weight`, `nav_keyboard_pct`, `cheatsheet_count`, plus a `window` selector (today/week/month/all) and a `records` object (`fastest_burst_wpm`, `busiest_keystroke_day`, `best_keyboard_day`, each `{value, day}`).

## The house style you must design within

This plugin must look like it belongs in Omarchy's shell, not like a generic QML app. Before proposing anything, explore the *installed* shell (not this repo) for the actual design system and reusable patterns:

- `/usr/share/omarchy/shell/Commons/Style.qml` and `Color.qml` — spacing scale (`Style.space(n)`), font tokens, corner radius, the color palette (incl. `Color.accent`, `Color.popups.*`) you must use instead of hardcoded hex values.
- `/usr/share/omarchy/shell/Ui/WidgetButton.qml`, `BarIconButton.qml`, `OpticalGlyph.qml` — bar-strip button/icon conventions (this plugin's `BarWidget.qml` already uses `WidgetButton`; keep using it, just consider icon vs. text content).
- `/usr/share/omarchy/shell/Ui/Panel.qml`, `KeyboardPanel.qml`, `PanelKeyCatcher.qml`, `BorderSurface.qml` — the popup chrome this plugin's `StatsPanel.qml` already extends; you're designing *inside* that card, not replacing it.
- Look at a few real first-party panels for inspiration on data-dense but native-feeling layouts, e.g. `/usr/share/omarchy/shell/plugins/panels/bluetooth/Panel.qml`, `.../audio/Panel.qml`, `/usr/share/omarchy/shell/Ui/SpeedTestOverlay.qml` (has a dial/arc gauge and simple filled-bar patterns worth stealing conventions from, not copying wholesale).
- Also glance at the other locally-installed third-party plugins under `~/.config/omarchy/plugins/*/Panel.qml` for how community authors keep things native-looking.

Do not invent a new visual language. Reuse `Style`/`Color` tokens and existing shell component patterns (bars, dials, borders, spacing) so this plugin is visually indistinguishable in *quality* from a first-party one.

## What "design the visualization" means here

The current panel is functional but flat: five text lines and a text list. Your job is to make the data actually legible at a glance — this plugin exists to tell someone "am I actually using the keyboard workflow or not," so the keyboard-vs-mouse split and the WPM number are the hero metrics. Concretely think about, and take a position on:

1. **Compact bar-strip label** (`BarWidget.qml`'s one-line text) — is text-only right, or would a tiny inline glyph/icon read faster at a glance in the bar strip? Keep it short; bar real estate is precious.
2. **Popup panel hero metrics** — a visual (not just numeric) treatment for the keyboard/mouse split (e.g. a filled two-segment bar, not just "⌨25%/🖱75%" as text) and for WPM (e.g. against typical typing-speed bands, or just a clean large number — your call, justify it).
3. **Records / "Best of the best"** — currently a plain bulleted list; does it deserve a small leaderboard/card treatment, given it's the "personal best" hook mentioned in the README?
4. **Window switcher** (Today / This week / This month / All-time) — currently just changes what text renders; is there a native-feeling way to make the active window visible without adding new interactive chrome the widget doesn't already support (check whether `windowKey` is even user-switchable from the panel today, or only from plugin settings — read `manifest.json`'s `barWidget.schema` and `BarWidget.qml` again before assuming).
5. **States**: not-connected (daemon down), connected-but-no-data-yet, and the full-data state each need their own explicit look — don't just design the happy path.
6. Respect the plugin's stated privacy stance (no raw content) — nothing you design should imply per-keystroke detail, only the aggregates that exist.

## Deliverables

1. **A written design spec** — save it as `DESIGN.md` at the repo root (create it; this is the one file you're allowed to write, as documentation, not code). For each of `BarWidget.qml` and `StatsPanel.qml`, give the development agent everything it needs without ambiguity: the exact component tree (which shell types to use — `WidgetButton`, `BorderSurface`, plain `Rectangle`/`Row`/`Column`, etc.), which `Style`/`Color` tokens for spacing/color, exact copy/labels, and how each data field maps to what's drawn, for every state in point 5 above. Where you propose something novel (e.g. a custom split-bar), describe its geometry precisely enough to implement (dimensions in `Style.space(n)` units, colors, corner radius) rather than just naming a concept.
2. **An HTML mockup artifact** (via the `Artifact` tool) showing the proposed bar-strip label and the full popup panel, ideally for a couple of the states above (e.g. full-data + not-connected), so the human can eyeball it before any QML is touched. This is a communication aid, not a spec — it doesn't need to be pixel-perfect Quickshell rendering, just close enough in layout/color/type to judge the idea. Load the `artifact-design` skill before building it, and give it a real dark UI background (this shell is dark-themed) rather than a plain white canvas.

Do not touch `BarWidget.qml`, `StatsPanel.qml`, or `StatsFormat.js`. If you're genuinely torn between two directions, use `AskUserQuestion` once to resolve it rather than hedging in the spec — don't over-ask.

Finish by reporting, in under 300 words: the artifact URL, a one-paragraph summary of the direction you took and why, and confirmation that `DESIGN.md` is written.
